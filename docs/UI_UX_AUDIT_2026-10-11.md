## 우선 처리 항목의 구체적 근거

### U01 — 최신 결과를 확인해도 근거를 볼 수 없는 상태

10/11 점검에서 CDN 목록은 `ddc4483acdd78555148e`(생성 10/11, 버핏 조건 충족 47개), 서버는 `a44945d27014caff69b5`(생성 10/09, 57개)였다. 양쪽 가격 거래일은 모두 10/08이다. 개수 감소 자체를 오류로 판단하지 않는다.

최신 목록 버전으로 `383220.KS` 근거 요청 시 HTTP 409 `snapshot_changed`를 확인했다. 실제 모바일에서는 첫 후보 경동나비엔의 선정 근거→‘최신 결과 확인’을 눌러도 ‘이전 자료가 응답했으므로 현재 결과를 유지한다’는 안내와 근거 오류가 남았다. [실화면](audits/2026-10-11/gurus-buffett-recheck.png), [화면 기록](audits/2026-10-11/recheck-gurus-buffett.json).

**개선:** 목록과 근거가 같은 검증 버전으로 게시되게 한다. 단기적으로 기존 수동 게시 절차에 동일 버전·5개 전략 근거 검증을 명시하고, 후속으로 공유 백엔드의 게시 완료 기준에 연결한다. 409 방어와 구버전 되돌림 방어를 제거해서 통과시키지 않는다. 프런트는 사용자가 이해할 수 있는 ‘선정 근거 게시 대기’와 마지막 확인 상태를 표시하고 반복 클릭을 유도하지 않는다.

관련: `src/api.js`, `src/staticData.js`, `src/guruInvestingView.js:82`, `docs/GURU_HEATMAP_QA_2026-10-07.md`, `docs/decision-log.md`의 10/08 게시 공백. 공유 백엔드 수정은 별도 저장소 분석이 선행되어야 한다.

### U02/U03 — 관심종목 저장과 조회 범위

**저장 실패:** 격리한 브라우저에 삼성전자/NVDA/AAPL을 저장하고 해당 저장 키의 `setItem`만 실패시켰다. 삼성전자 삭제 시 메모리는 먼저 변경되지만 저장은 실패한다. 이름순 정렬 후 삼성전자가 사라지고, 새로고침하면 저장된 3개가 돌아왔다. 서버 장애나 실제 사용자 저장소를 조작한 테스트가 아니다.

**한도:** 자체 20개 목록에서 삼성전자 상세의 하트를 누르면 21개가 된다. 관심 화면에는 21행이 있지만 `/api/quotes`에는 앞 20개만 요청하며 마지막 AAPL은 가격·등락률이 `-`다. [재현 값](audits/2026-10-11/targeted-findings.json), [21행 화면](audits/2026-10-11/watch-limit-21.png).

**개선:** 모든 등록·편집·삭제 경로에서 저장 성공 후 상태를 확정하거나 실패 시 원상복원한다. 기존 편집기의 20개 기준을 새 등록에 일관되게 적용한다. 이전 버전에서 이미 저장한 20개 초과 목록을 자동으로 잘라서는 안 된다. 기존 초과 목록은 보존하고 조회 범위·정리 방법을 명시한다. 전체 초과 항목 시세 조회가 필요하면 요청 예산을 검토한 별도 작업으로 진행한다.

관련: `src/main.js:133`, `:659`, `:773`, `:781`, `:804`, `:1155`, `:1406`, `src/storage.js`, `tests/storedLists.test.mjs:38`. 상세 하트의 기존 저장 실패 rollback을 재사용할 수 있는지 먼저 검토한다. Native 비동기 저장 실패는 실제 Toss 검증도 필요하다.

### U04/U05/U06 — 값의 정확성과 해석 근거

**PICK:** 실제 37개 평가 기록, 상승 21개로 57%, 평균 5.5235%로 화면 +5.52%가 맞았다. 그러나 여러 선정일·같은 회사의 반복 기록을 포함한 산술평균이라는 설명, 보유기간 차이, 배당·비용 미반영, 실제 포트폴리오 수익률과의 구별이 부족하다. 목록 필터와 상단 전체 집계의 범위도 구분해야 한다. 계산식을 바꾸는 작업이 아니다. `src/pickLedger.js:281`, `:316`, `src/homeExtras.js:220`.

**그린블라트:** 실제 선익시스템 응답의 연간 ROA 26.4%/PER 6.84와 현재 TTM ROA 2.48%/PER 40.98은 서로 다른 기간의 값이다. 현재 모델이 TTM 응답의 `generatedAt`과 `fieldMeta`를 버려 화면에는 제공처·조회시각이 없다. Yahoo Fundamentals, 조회 생성 시각, `asOf:null`에 대한 ‘자료 기준시각 미제공’을 표시해야 한다. 연간 기준일을 TTM 기준일로 복사하지 않는다. `src/guruInvestingModel.js:25`, `src/guruInvestingView.js:76`, `src/guruInvestingExtensions.js:20`.

**반도체:** 실제 점검에서는 추이와 국가 자료 모두 2026-09다. 다만 개별 요청/캐시 갱신 경계에 추이는 9월, 국가 자료는 8월이면 품목 키만으로 연결된다. 국가별 증감을 9월의 설명이나 기업 조사 근거로 사용하지 않도록 기준월 일치를 검사한다. 차트는 유지하고 다른 기준의 국가 자료임을 알려야 한다. `src/exportMomentumModel.js:490`, `src/exportMomentumView.js:404`, `:455`, `:1140`.

## 테스트 증거와 한계

실행한 기존 테스트:

```sh
npm run test:e2e:live
node --test tests/guruInvesting.test.mjs tests/guruFive.test.mjs tests/export_momentum.test.mjs tests/pick_management.test.mjs tests/pickLedgerLoading.test.mjs
```

운영 E2E **5/5**, 42.8초, 재시도 없이 통과: 삼성전자 검색·가격 대응, 실제 DRAM 12개월, PICK 집계 대응, 화장품 API→모델→UI, 거장 5전략 스냅샷 범위. Node **49/49** 통과. 거장 운영 테스트는 개별 선정 근거를 열지 않으므로 U01을 잡지 못했다. 다음 개선에서 반드시 근거 버전 검증을 보강한다.

이 환경에서는 `E2E_BASE_URL=https://chart-view-toss.onrender.com`, 세션의 `E2E_PROXY_SERVER`, 한국어 폰트용 scratch `FONTCONFIG_FILE`을 사용했다. 브라우저 탐색의 API 응답은 세션 프록시를 통해 실제 응답을 전달했으며 정상 데이터 대신 fixture를 넣지 않았다. 저장 실패 테스트만 명시적으로 조건을 주입했다. 폰트 설정 문제는 실행 환경에서 해결했고 앱 CSS는 바꾸지 않았다.

[경로 스냅샷](audits/2026-10-11/survey-summary.json)의 `ready:false`나 탐색 도구 timeout을 제품 장애/속도 점수로 해석하면 안 된다. 철강·석유제품은 후속 재진입에서 정상 차트, 반도체 가격은 최초 실패 안내 후 후속 조회에서 정상 자료를 확인했다. 일부 삼성전자 선택 모듈도 재진입 시 연결 실패와 재시도를 보였지만 다른 재무 정보는 유지됐다. 공급자·서버·실행 환경 중 원인은 분리하지 못했으며 통제된 성능 측정을 하지 않았다.

이번에는 OS 의존 라이브러리가 없어 WebKit을 실행하지 못했다. **iOS Safari, 실제 Android/iOS Toss Sandbox, native 저장·공유·외부 브라우저는 미검증**이다. 전체 `qa:prepush`도 이번 문서 작업에서는 실행하지 않았다. 웹 탐색 결과를 실제 Toss 출시 인증으로 확대하지 않는다.

새 LLM 호출·API 키·유료 인프라는 추가하지 않았다. tester-army/e2e 런타임은 이번 점검에서 실행하지 않았고 기존 Playwright와 Codex 탐색·검토를 사용했다. 테스트 통과 수는 전체 사용성 문제의 부재를 의미하지 않는다.
