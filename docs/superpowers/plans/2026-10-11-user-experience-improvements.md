# 차트뷰 토스 사용자 경험 개선 실행 계획

> **For agentic workers:** 구현 시 `superpowers:executing-plans` 또는 `superpowers:subagent-driven-development`를 적용하고 아래 완료 조건을 작업별로 검증한다. 체크박스는 구현 완료 때만 체크한다.

**Goal:** 기존 compact UI와 데이터 수집·배포 구조를 유지하며 사용자가 분석 근거를 신뢰하고, 관심종목을 일관되게 저장하고, 작은 화면에서 조사·공유를 마칠 수 있게 한다.

**Architecture:** 현재 Vite/vanilla JS 화면·API client·저장 helper·Playwright를 확장한다. 데이터 계산과 공급자 계약은 유지하며 실패/기간/버전/상태 경계를 보강한다. 거장 게시 문제만 공유 백엔드와 별도 조정한다.

**Tech Stack:** Node 24.x, 기존 Node test, Playwright 1.55, 기존 GitHub Actions와 Render 검증 절차. 새 LLM API, 테스트 엔진, 유료 서비스, 자동 배포 hook은 추가하지 않는다.

**Spec:** [2026-10-11 사용자 관점 점검 보고서](../../UI_UX_AUDIT_2026-10-11.md). 이후 사용자가 우선순위별 구현과 작업 계속을 요청해 실행 중이다. 구현 결과와 운영·실기기 잔여 조건은 [실행 보고서](../../UX_IMPROVEMENTS_2026-10-11.md)에 별도로 기록한다.

## 실행 순서와 범위

| 단계 | 작업 | 사용자에게 생기는 변화 | 규모·의존 |
|---|---|---|---|
| 1. 저장·근거 신뢰 | T1, T2 | 근거를 열 수 있고, 관심 등록/삭제 결과가 일관됨 | T1 중, T2 중~대·백엔드 조사 선행 |
| 2. 숫자 해석·회복 | T3, T4, T5 | 수익률/TTM/수출 기준을 이해하고 부분 실패에서 복구 | 각 중, T3/T4는 별도 파일이면 병렬 가능 |
| 3. 모바일·공유 동선 | T6, T7, T8 | 공유한 탭 유지, 읽기·종목 식별·연구 재방문 개선 | 소~중, 데이터 변경 없이 분리 배포 가능 |
| 4. 후속 편의 | T9 | 관심 순서/뉴스/조건을 적은 조작으로 다룸 | 중, 관찰한 불편부터 작은 변경 |
| 매 단계 | T10 | 변경한 커밋에 회귀 증거가 남음 | 필수, 모든 변경에 적용 |

규모는 상대 비교이며 일정 약속이 아니다. T2 백엔드 게시 조사와 T1 프런트 저장 개선은 병렬 진행할 수 있다. 첫 적용 묶음은 U01~U03, 두 번째는 U04~U06/U09로 제한해 원인 추적과 되돌리기를 쉽게 한다.

전역 제약:

- 하단 메뉴 4개, 시장 중심 홈, compact 행, 현재 route/Back/safe-area 유지.
- 새 자료가 늦으면 검증된 이전 자료를 실제 기준일과 함께 유지. 가격 최신성·캐시 보장 약화 금지.
- 실제 0/음수/미제공 구별, 연간/TTM·연결/별도·기준월/통화/단위 유지.
- 원인별 부분 재시도, 늦게 도착한 응답의 다른 화면 변경 차단.
- 개인 관심 목록·저장 연구는 공개 URL/공유 payload에 넣지 않음.
- 기존 초과 관심 목록 자동 잘라내기 금지. 외부 API 요청 확장은 별도 예산 검토.
- 기존 테스트 확장 우선, 기능별 회귀 테스트 포함, 실패를 조건 완화로 숨기지 않음.

**Done:** 실패 전후 저장 바이트와 화면이 일치하거나 실패한 초안으로 명확히 구분된다. 신규 21번째 등록은 모든 경로에서 같은 결과를 낸다. 기존 40개 복구 계약은 유지된다.

## T2 — 거장 목록과 근거의 게시 일치 (U01)

**Files:** 프런트 `src/api.js`, `src/staticData.js`, `src/guruInvestingView.js`; 기존 `tests/guruInvesting.test.mjs`, `tests/e2e/guru-coverage.spec.mjs`, 운영 E2E 파일. 공유 백엔드의 실제 게시 workflow/캐시 writer/근거 API 파일은 별도 저장소 조사 후 확정한다.

**Contract:** 화면 목록의 `snapshotVersion`과 근거 요청/응답의 버전·종목이 같아야 한다. 새로운 버전의 종목 감소는 허용하되 이전 생성 시각으로 되돌리지 않는다.

- [x] 기존 백엔드 수집→CDN 게시→Render 반영 순서를 읽고 오늘의 409 재현을 운영 이력과 대조한다. 현재 checkout을 그대로 backend 수정 경로로 가정하지 않는다.
- [x] `CDN newer/backend older`, 동시 게시, 전략별 자료 미제공, 근거 지연을 기존 결정론적 테스트에 추가한다.
- [x] 프런트의 기존 409/older guard를 유지하고 ‘근거 게시 대기’ 안내와 재시도 상태를 이해하기 쉽게 정리한다. 버전이 다를 때 다른 근거를 붙이지 않는다.
- [x] 단기 복구 절차에 정확한 검증 backend revision, 목록 버전, 각 전략의 대표 근거 200 및 고의 이전 버전 409 검증을 명시한다.
- [x] 지속 해결은 기존 배포 구조 안에서 목록과 근거의 동일 버전 게시 완료를 확인하는 방식으로 설계한다. 데이터 원본별 독립 최신화와 게시 readiness를 구분한다. 운영 구조 변경은 실제 공유 저장소 분석 결과로 별도 검토한다.
- [x] 운영 smoke를 스냅샷 개수 검사에서 실제 후보 근거 열기까지 확장한다. 후보 0/미게시 전략은 이유를 검증하고 임의 종목으로 성공 처리하지 않는다.

**운영 완료 조건(미완료):** 게시 완료로 표시된 5개 전략의 실제 후보 근거가 동일 버전으로 열린다. 배포 전후 경계에서는 설명 가능한 대기/재시도이며 혼합 근거나 구버전 rollback이 없다. 프런트만 수정하고 서버 게시 공백까지 해결했다고 보고하지 않는다.
