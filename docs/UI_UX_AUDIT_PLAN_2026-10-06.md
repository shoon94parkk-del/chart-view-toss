# 차트뷰 토스 실제 사용 점검 및 개선 계획

점검일: 2026-10-06 · 대상: https://chart-view-toss.onrender.com

## 1. 결론

검색 → 종목 상세 → 관심 등록 → 비교 → 공시 확인과 저장으로 이어지는 주요 기능은 실제로 동작했다. 다만 **사용자가 숫자를 믿고 해석하는 데 영향을 주는 오류**, **원문 이동 실패**, **정보를 찾기까지 필요한 긴 스크롤**, **화면 간 선택 상태 단절**이 남아 있다.

개선 순서는 다음과 같다.

1. **날짜·가격 기준·뉴스 원문 이동을 바로잡는다.**
2. **상세와 히트맵의 탐색 흐름을 줄이고, 이전 화면의 선택을 유지한다.**
3. **필터·상태·표·데스크톱 배치를 정리한다.**

이번 작업은 실제 화면 점검과 수정 계획 수립이다. 제품 코드 변경과 배포는 진행하지 않았다.

## 2. 점검 기준과 범위

- 실제 배포 화면에 표시된 버전: **0.15.0**.
- 관찰한 배포 자바스크립트: **index-DfF9_tOW.js**.
- 화면 너비: 모바일 **390px·320px**, 데스크톱 **1440px**. 모바일 높이는 담당 브라우저에 따라 844px 또는 900px.
- 사용자의 브라우저 저장 데이터를 건드리지 않는 별도 Playwright 브라우저에서 실제 클릭·입력·새로고침·뒤로가기를 수행했다. 데이터나 날짜를 모의로 주입하지 않았다.
- 홈, 종목 상세, 분석 메뉴의 15개 화면과 주요 선택·저장·비교 흐름을 확인했다. 모든 종목의 모든 조합이나 모든 외부 제공처의 숫자를 재검산한 전수 검사는 아니다.
- `browser-automation-skill`, `playwright`, `ui-ux-pro-max`의 브라우저 검증·모바일 가독성·접근성 기준을 참고했다.
- 수정 시에는 현재 배포 기준의 소스를 사용해야 한다. 점검 당시 로컬 체크아웃은 0.10.3이었으며, 읽기용으로 확인한 `origin/main`은 `bafc9c421bc8fcde654c55d292bfea1347d570a9`였다. 이 해시를 Render의 실제 배포 커밋으로 별도 확정한 것은 아니다.

## 3. 우선 수정할 문제

### A1. 직접 지정한 종료일 다음 날까지 수익률에 포함됨 — P1, 재현된 기능 오류

**현재**

삼성전자와 SK하이닉스 비교에서 시작일 `2026-09-01`, 종료일 `2026-10-01`을 입력했지만 결과의 마지막 날짜는 두 종목 모두 `2026-10-02`였다. 다른 종료일 `2026-10-05`에서도 결과에 `2026-10-06`이 포함됐다.

실제 요청에도 `start=2026-09-01&end=2026-10-01`이 전송됐고, 응답의 `endDate`는 `2026-10-02`였다. 결과 수익률은 삼성전자 +5.75%, SK하이닉스 +8.74%였다. 이 수익률은 입력한 종료일의 결과로 받아들이면 안 된다.

앞서 잘못된 날짜로 표시된 오류 문구도 유효한 날짜를 적용한 뒤 남아 있었다. 현재 원격 소스의 날짜 제출 처리에는 유효 입력 후 기존 오류를 지우는 처리가 보이지 않는다.

**개선**

- 서버가 종목 시장의 거래일을 기준으로 요청 구간을 적용하고, 반환 관측값이 종료일을 넘지 않도록 검증한다.
- 제공처의 종료일 포함/제외 규칙과 UTC 변환을 조사해 원인을 고친다. 화면에서 날짜만 바꾸는 것으로 처리하지 않는다.
- 요청 구간과 실제 관측 구간을 함께 표시한다. 휴장일이면 마지막 실제 거래일을 사용했다는 설명을 붙인다.
- 유효한 날짜 제출 시 이전 오류를 지운다. 결과는 차트·표·공유 화면이 같은 구간을 사용한다.

**완료 기준**

평일 종료일, 휴장일, 시작일=종료일, 한·미 종목 혼합, 잘못된 입력 후 정상 입력에서 모든 관측일이 요청 구간 안에 있어야 한다. 날짜 수정 후 실제 API 응답과 화면을 함께 확인한다.

증거: [입력일과 결과일이 다른 화면](../output/playwright/current-audit-20261006/chart-range-mismatch.png).

### A2. 최신 제공 시세를 정규장 종가로 단정함 — P1, 재현된 기준 표시 모순

**현재**

삼성전자 가격 카드가 `273,000원 · 10.6.20:20 KST`를 **정규장 종가**로 표시했다. 같은 카드의 출처를 펼치면 최신 제공 시세는 정규장 종가와 다를 수 있다고 설명하고, 스크리너의 `2026-10-06 장마감 수집 종가 272,000원`도 함께 표시했다.

이것은 **가격 기준 라벨의 모순**이다. 273,000원 또는 272,000원 중 어느 숫자가 틀렸다고 확정한 것은 아니다.

**개선**

- 제공처가 정규장 종가임을 명확하게 보장한 필드에만 ‘정규장 종가’를 쓴다. 나머지는 ‘제공처 최신 시세’로 표시한다.
- 관측 시각·조회 시각·시장 세션·가격 출처를 구분한다.
- 장마감 수집 값은 독립된 기준으로 보여주고, 차이를 사용자가 해석할 수 있게 한다.
- 같은 가격 종류의 문구를 상세·관심·히트맵·IDEA·PICK에서 일관되게 사용한다. IDEA와 PICK의 다른 가격도 출처와 기준일을 먼저 검증한다.

**완료 기준**

정규장·시간외·기준 미제공 시세가 올바른 라벨로 표시되고, 제공처 최신값과 수집 종가가 달라도 설명이 모순되지 않아야 한다.

증거: [삼성전자 시세 기준](../output/playwright/current-audit-20261006/detail/price-provenance-390.png).

### A3. 일부 뉴스 원문을 열 수 없음 — P1, 재현된 기능 오류

**현재**

관심종목 뉴스의 연합뉴스TV 기사 버튼을 눌러도 원문이 열리지 않고 `외부 링크를 열지 못했어요. 잠시 후 다시 시도해주세요.`가 나타났다.

버튼의 실제 주소는 `http://www.yonhapnewstv.co.kr/news/MYH20261006212550ecY`였다. 뉴스 목록에는 다른 `http` 주소도 있었다. 현재 링크 열기 함수는 `https:`만 허용하므로 이 주소는 제공처의 일시 지연 여부와 관계없이 거절된다.

**개선**

- 뉴스 수집·정규화 단계에서 제공처가 지원하는 HTTPS 원문 주소를 검증하여 저장한다. 모든 HTTP 주소를 확인 없이 HTTPS로 치환하지 않는다.
- 원문 주소가 사용할 수 없는 상태라면 카드의 이동 가능 여부와 이유를 정확하게 표시한다.
- 잘못된 주소와 일시 연결 실패를 구분한다. 주소 거절에는 ‘잠시 후 다시 시도’를 반복 안내하지 않는다.
- 기존 외부 링크의 프로토콜 제한과 Toss 환경 처리를 유지하며 해결한다.

**완료 기준**

HTTPS 기사, HTTP로 수집됐지만 HTTPS 원문을 지원하는 기사, 지원하지 않는 주소 각각에서 실제 원문 열기 또는 정확한 대체 안내가 동작해야 한다. 허용하지 않는 프로토콜은 계속 차단한다.

증거: [원문 이동 실패 안내](../output/playwright/current-audit-20261006/news-mobile.png).

## 4. 사용자 흐름을 줄이는 개선

### B1. 종목 상세에서 비교와 저장한 근거를 찾기 어려움 — P2

삼성전자와 하이닉스 비교 결과까지 불러온 상태의 페이지 높이는 390px에서 **10,148px**, 320px에서 **11,057px**였다. 질문 입력칸은 각각 Y6,546px·Y6,977px에 있었다. 산업·공급망 설명은 기본으로 펼쳐져 있다.

상단 바로가기 5개는 정상 동작했지만, 공시 실적 안의 최근 8분기·실적의 질·변화·저장한 근거를 바로 선택하기는 어렵다.

**바뀔 구성**

- 종목 상단: 이름·티커 → 핵심 시세 → 관심·비교 → 간단한 실적 요약.
- 공시 실적: 최신 보고서와 매출·영업이익·이익률 변화 요약을 먼저 보여준다. 8분기·실적의 질·공시 변화·저장한 근거는 내부 바로가기로 접근한다.
- 공시 비교: 질문 입력과 비교 회사 선택을 함께 두고, 결과 바로 아래에 근거 저장과 원문 확인을 배치한다. 상단 ‘공시 비교’ 바로가기로 즉시 이동할 수 있다.
- 회사·산업: 핵심 사업·업종·관계 확인 상태만 요약하고, 긴 공급망 설명과 원자료는 펼쳐 본다.
- 숫자의 연결/별도, 누적/개별 분기, 통화, 공시 기간은 주요 수치 옆에 남긴다. 접어 두더라도 원문 접근은 유지한다.

메인 바로가기를 더 늘려 모바일을 좁게 만들지 않고, 실적 영역 안에서 필요한 위치를 찾게 한다.

**완료 기준**

320px·390px에서 비교 입력과 저장 근거를 각 바로가기 한 번으로 찾을 수 있어야 한다. 접기·펼치기 후 초점이 유지되고 고정 메뉴에 가리지 않아야 한다. 공시 비교의 지원 범위 안내와 해외 종목의 경계도 유지한다.

증거: [320px 상세 비교 화면](../output/playwright/current-audit-20261006/detail/layout-comparison-320.png).

### B2. 홈에서 선택한 히트맵 시장이 이어지지 않음 — P2, 재현된 흐름 단절

홈 히트맵에서 **미국**을 선택하고 `히트맵 보기`를 누르면 전체 화면은 **한국**으로 열린다. 전체 미국 히트맵에서 엔비디아 상세에 들어갔다 뒤로 돌아왔을 때 미국 선택은 유지됐다.

**개선:** 홈 → 전체 지도에 시장을 전달하고, 같은 탐색 안에서는 시장·선택 업종·스크롤을 이어서 보여준다. 공유 주소에서도 시장을 전달하는지 확인한다.

**완료 기준:** 홈 미국 → 전체 미국 → 종목 상세 → 뒤로가기에서 처음 탐색한 시장과 위치가 유지되어야 한다.

### B3. 작은 히트맵 종목은 누르기 어렵고 업종 목록이 멀리 나타남 — P2

320px 미국 히트맵에서 Salesforce 칸은 약 **28.7×18.4px**, Cisco 칸은 약 **28.7×22.5px**였다. 문서 전체가 가로로 넘치지는 않았지만 일부 종목의 터치 면적은 작았다.

한국 지도에서 반도체 제목을 누르면 종목 목록이 지도 전체 아래에 나타났다. 클릭한 제목은 화면 Y160px, 목록 제목은 Y700px에 있었고 첫 종목의 일부가 고정 하단 메뉴 뒤로 내려갔다. 펼쳐졌다는 변화가 충분히 눈에 들어오지 않는다.

**개선:** 지도 비중은 보존하되 `지도 / 목록` 전환을 제공한다. 업종을 누르면 화면 안에서 해당 업종의 목록을 바로 볼 수 있게 펼치거나 시트로 열고 초점을 옮긴다. 목록 행은 편하게 누를 수 있는 최소 44px 높이를 목표로 한다.

**완료 기준:** 320px에서도 지도에 있는 모든 종목을 목록에서 이름·가격·날짜와 함께 선택할 수 있어야 한다. 색 외에 등락 수치를 제공하고, 열기·닫기·키보드 초점·상세 복귀를 검증한다.

증거: [업종 펼침 위치](../output/playwright/current-audit-20261006/heatmap-sector-mobile.png), [미국 320px 지도](../output/playwright/current-audit-20261006/heatmap-us-320.png).

### B4. IDEA에서 상세를 보고 돌아오면 펼친 근거가 접힘 — P2

IDEA의 근거를 펼치고 해당 종목 상세에 들어간 뒤 돌아오면 근거가 접힌다. 펼친 모바일 페이지는 약 4,616px여서 이전 후보와 내용을 다시 찾는 부담이 있다.

**개선:** 같은 탐색 안에서 펼친 후보와 스크롤 위치를 유지한다. 데이터가 갱신되며 후보가 사라진 경우만 변화를 알려준다. 저장 여부와 임시 화면 상태는 구분한다.

**완료 기준:** 후보 근거 펼침 → 상세 → 뒤로가기에서 같은 후보의 근거가 열린 상태로 복원되어야 한다.

터치 영역이 작다는 문제를 모든 버튼에 일반화하지 않는다. 상세의 표본 주요 버튼은 44px 이상이었고, 종목 선택 창은 Escape로 닫힌 뒤 ‘종목 변경’ 버튼으로 초점이 복원됐다.

## 6. 실행 순서와 검증

### 1차: 숫자와 이동의 신뢰

대상: **A1·A2·A3**, PICK 집계 범위.

- 최신 배포 기준 소스를 확보한 뒤 날짜 처리와 뉴스 URL의 원인을 수정한다. 공유 백엔드의 날짜 계약은 웹 클라이언트와 함께 확인한다.
- 행동 오류별로 해당 문제를 재현하는 회귀 검사를 추가한다.
- 실제 화면에서 같은 종목과 입력일로 재확인한다. 뉴스는 주소 형식이 다른 사례를 각각 검증한다.

### 2차: 찾기와 복귀

대상: **B1~B4**, 모바일 필터와 표.

- 종목 상세의 요약·비교·저장 흐름, 업종 목록 접근, 시장 전달과 복귀 상태를 개선한다.
- 320px·390px에서 핵심 작업까지의 클릭 수와 스크롤 위치를 기록한다.
- 접기·펼치기·뒤로가기·초점·공유 수신을 실제 조작한다.

### 3차: 화면 통일과 넓은 화면 활용

대상: 상태 문구·단위·중복 제목·데스크톱 배치·뉴스 근거 표현.

- 재사용 가능한 가격 기준·상태·원문·로딩 컴포넌트로 표현을 통일한다.
- 주요 경로를 다시 확인한 뒤 배포된 버전과 실제 화면을 검증한다. 배포가 요청된 구현 단계에서 수행할 절차다.

각 단계는 동작 수정의 회귀 검사, 전체 테스트, 빌드, 관련 모바일 QA를 통과한 뒤 다음 단계로 진행한다. 웹 브라우저 결과만으로 Android/iOS의 실제 Toss 출시 검증을 완료했다고 판단하지 않는다.

## 8. 로딩과 추가 확인의 경계

- 비교 기간을 변경하다 일부 요청이 실패했으며 기존 결과와 이전 기간이 유지됐다. 6개월은 이후 다시 조회하여 정상 결과를 확인했다. 5년·전체 기간의 최종 재시도 성공은 확인하지 않았다.
- 공급망 기사는 처음에 제공처 지연과 재시도 버튼을 표시했고, 이후 ‘구체적 계약·납품 단서 없음’으로 바뀌었다. 이를 공급 관계가 없다는 확정 판단으로 바꾸면 안 된다.
- IDEA의 일부 공시·관계 보강은 캡처 때 로딩 중이었다. 모든 제공처의 최종 완료를 주장하지 않는다.
- 이번 측정은 실제 흐름과 배치 점검이다. Render 콜드 스타트, 통제된 반복 응답 시간, Core Web Vitals의 새 성능 기준치를 측정한 것은 아니다.
- 구현 후 느린 구간을 다시 측정할 때는 콜드 스타트/활성 상태, 첫 방문/저장값 방문을 분리한다. 실패 시 이전 결과·현재 적용 기간·재시도 상태를 함께 보여준다.
- 공시의 독립 재계산, 새 공시·정정 공시 발생, 오프라인·제공처 장애, 모든 삭제·초기화 분기, 실제 Android/iOS 네이티브 공유·뒤로가기는 추가 검증 범위다.
