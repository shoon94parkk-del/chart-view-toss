## Important I1 — HTTP-200 provider failures become false empty chart evidence

`src/main.js:1625–1634` checks only Promise rejection. Every resolved payload passes `rows: value.items || [], newsState:'ready'` to the new evidence controller. The real backend returns HTTP 200 even if a provider fails: `news_service_v37.py:364–395` supplies `groups[].status:'error'` and `errors` while `items` can be empty. Consequently the new chart section says `현재 조회된 범위에 확인된 관련 기사가 없어요`, disables markers and offers no recovery in the detail news section. This misstates unavailable evidence as an empty successful search.

Reproduction payload: `{items:[],groups:[{symbol:'AAPL',status:'error',items:[]}],errors:[{symbol:'AAPL',code:'provider_error:Timeout'}],requestedCount:1}`. Pass it through the current fulfilled `loadDetailNews` branch. The reader model correctly classifies it `error`; the detail branch supplies `ready` and zero events. A small Node adapter probe confirmed those states without any provider call. Fix: inspect backend envelope failure metadata, pass truthful error/partial status, preserve usable rows for partial failures and expose explicit retry. Add an API-envelope-to-detail-evidence browser regression.

## Important I2 — the new news retry control reuses a cached error response

`src/main.js:1671,1690` wires `onRetry:renderNews`, and `src/api.js:71` caches all HTTP-200 personalized-news responses for 60 seconds with no force option. `src/newsReaderModel.js` detects provider failure/partial payloads, so its new retry button is visible, but clicking it simply reloads the cached failed response. An explicit action cannot reach a recovered backend until the browser TTL expires.

A targeted Node probe imported the real `personalizedNews` wrapper, supplied a mocked fetch returning the error envelope above on its first call and success on the next, then invoked the wrapper twice exactly as renderNews does. Actual output: `{"fetchCalls":1,"firstFeed":"error","secondFeed":"error"}`. This is independent of the backend's existing 300-second provider cache: even an already-recovered backend is not contacted. Fix: add an explicit force option for the action and/or avoid caching error/partial envelopes, preserving normal same-visit deduplication. Test the HTTP-200 failure form as well as transport failures. The backend's existing provider-cache TTL remains an external contract and should not be represented as immediate forced provider refresh.

## Minor M1 — the required US four-day coverage disclosure is absent

The approved spec explicitly requires disclosure of the US four-day collection window. Backend `news_service_v37.py:273` uses `today - timedelta(days=4)`. The new chart evidence copy (`src/chartEvidence.js:142`) only says it shows currently fetched articles; no four-day text appears in this module, main.js or the news reader. A one-year chart with a few recent markers can therefore obscure the much shorter evidence coverage. Add US-specific visible collection-window wording, preferably alongside the marker list, without implying complete coverage even within that window. Root is coordinating a narrow module follow-up.

## Minor M2 — detail chart ignores already-returned group-only articles

`src/main.js:1633` sends only `items` into the chart adapter. Backend `items` is a ranked, investment-qualified highlights subset (`_balanced_highlights`, news_service_v37.py:169–203); `groups[].items` contains up to six verified-relation articles per requested symbol. A legitimate response may have `items:[]` and a nonempty success group. The new full reader shows that article, while its detail chart says no confirmed related article exists. A targeted pure-model probe with one dated HTTPS AAPL article in groups produced `readerArticles:1`, `detailMarkers:0`, `availableMarkers:1` when the group row was handed to the adapter. Feed the selected symbol's already-returned group rows, with URL deduplication, or disclose that chart evidence is restricted to highlights. This is a consistency/coverage issue; the spec does not explicitly require every returned article to be plotted.

## Minor M3 — integration tests omit their named period-change path and real failure envelope

The new chart E2E at `tests/e2e/moneytoring-ux.spec.mjs:91` names period changes but never clicks a period control, so it does not verify transfer from a removed area series to the replacement while markers are enabled. The summary retry test uses HTTP 503, which does not cover I1/I2. Add a realistic HTTP-200 provider-failure fixture, a group-only article case, selected-symbol API scoping and an enabled-marker period change. ## Final API/cache follow-up — coordinated provider retry contract

**Disposition remains PASS for the reviewed integration code; no new Critical, Important or Minor finding.** Reviewed the final frontend retry query/cache changes against the updated backend `news_service_v37.py` on base `934e0546f78e0e2ee0017b2923dc0cae49c7ad27`. The separate backend reviewer owns the backend's final verdict.

The browser now sends `force=true` only for explicit personalized-news retry and sets local `force:true`. The backend accepts that flag and maps it to `retry_errors_only=True`: a cached failed group may refresh while healthy and confirmed-empty groups retain the normal 300-second cache. The existing internal `_cached_fetch(force=True)` full-bypass contract remains intact. This coordinated endpoint change supersedes the earlier report's limitation that explicit retries could not refresh the backend's cached provider error.

The frontend caches only `newsResponseState(payload)==='ready'`. Failed and partial base-URL responses therefore cannot survive behind the distinct `force=true` retry URL and reappear on the next ordinary render. A successful retry URL is separate from the ordinary cache key, so the next normal render may make one normal API request; its successful result then uses the existing local cache. This is consistent with the tests and does not promise an extra provider refresh. Existing view-epoch guards, cleanup, source/summary identity and explicit-action-only retry callbacks are unchanged.
